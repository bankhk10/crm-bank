# Design Specification: Multi-Role Auto-escalation Approval Flow

## 1. Goal
ปรับปรุงระบบให้รองรับพนักงาน 1 คนที่มีหลายตำแหน่ง (Positions) และรับผิดชอบหลายเขต (Zones/Areas) พร้อมทั้งสร้างระบบการอนุมัติแบบ **Auto-escalation** ที่จะเช็คตำแหน่งสูงสุดของผู้สร้างรายการในเขตนั้นๆ เพื่อข้ามขั้นตอนการอนุมัติที่ต่ำกว่าโดยอัตโนมัติ

นอกจากนี้ จะมีการสร้าง **Test Menu (หน้าทดสอบระบบ)** เพื่อจำลองและตรวจสอบความถูกต้องของ Flow การอนุมัติทั้งหมด

## 2. Database Schema Changes
เนื่องจากระบบปัจจุบันตาราง `Employee` เก็บ `positionId` และ `responsibilityArea` แบบ 1-ต่อ-1 จะต้องเพิ่มตารางเชื่อม (Mapping Table) ดังนี้:

- **สร้างโมเดลใหม่ `EmployeePositionArea`**
  - `id`: CUID
  - `employeeId`: FK to Employee
  - `positionId`: FK to Position
  - `area`: String (เขตที่รับผิดชอบ)
  - `isActive`: Boolean

*หมายเหตุ: โครงสร้างของตาราง `Position` มีฟิลด์ `level` อยู่แล้ว (เช่น Sales=1, Regional Manager=2) ซึ่งจะถูกนำมาใช้เทียบความสูงของตำแหน่ง*

## 3. Auto-escalation Logic
เมื่อมีการสร้างเอกสาร (เช่น "Activity" ในหน้าทดสอบ) ระบบจะ:
1. รับค่า **ผู้สร้าง (Creator)** และ **เขต (Zone)** ของเอกสารนั้น
2. ค้นหาใน `EmployeePositionArea` ว่า Creator คนนี้ มีตำแหน่งอะไรบ้างใน Zone นั้น
3. ดึงค่า `Position.level` สูงสุดออกมา (Max Level)
4. กำหนดสถานะและลำดับการอนุมัติถัดไปตาม Max Level:
   - **Max Level 1 (เซลส์):** ส่งไปให้ ผจก.ภาค (Level 2) อนุมัติ
   - **Max Level 2 (ผจก.ภาค):** ข้ามการอนุมัติระดับเซลส์ (บันทึกสถานะว่า Auto-approved by Creator) และส่งไปให้ ผจก.แผนกบริหารงานขาย (Level 3) ทันที

## 4. Test Menu & UI (แผนการทดสอบ)
ตามที่คุณผู้ใช้เสนอมา แผนการทดสอบครอบคลุมการใช้งานหลักแล้ว แต่เพื่อให้รัดกุม 100% จึงได้รีวิวและเพิ่มข้อเสนอแนะ (ส่วนที่เน้นตัวหนา) ดังนี้:

### 4.1 หน้าจัดการสิทธิ์ (Role & Zone Assignment)
- สามารถกำหนดให้ ผู้ใช้งาน (User) มีกี่ตำแหน่ง และกี่เขตก็ได้

### 4.2 หน้าสร้างกิจกรรมทดสอบ (Activity Creator)
- ทดสอบสร้างกิจกรรม โดยมีการสุ่มข้อมูล (Mock Data)
- สามารถเลือกและเปลี่ยน "ผู้สร้างกิจกรรม (Creator)" ได้
- **[ข้อเสนอแนะเพิ่มเติม]: ต้องมีช่องให้เลือก "เขต (Zone) ของกิจกรรม" ด้วย** เพราะระบบจะต้องเช็คสิทธิ์แบบ Cross-check ระหว่าง (Creator + Zone) ตัวอย่างเช่น นาย ก. อาจเป็น ผจก.ภาค ที่เขต 1 แต่เป็นแค่เซลส์ที่เขต 2

### 4.3 หน้าแสดงผลและอนุมัติ (Approval Dashboard)
- แสดงรายละเอียดว่ากิจกรรมนี้ตอนนี้รอใครอนุมัติอยู่ (ตำแหน่งไหน)
- **[ข้อเสนอแนะเพิ่มเติม 1]: แสดง Audit Trail ให้ชัดเจน** ถ้าระบบทำการ Auto-approve ข้ามสเต็ปไหนไป ต้องมี Log แสดงบนหน้าจอว่า "ข้ามขั้นตอนอนุมัติระดับเซลส์ เนื่องจากผู้สร้างเป็นผู้จัดการภาค"
- **[ข้อเสนอแนะเพิ่มเติม 2]: แสดงรายชื่อผู้อนุมัติที่เป็นไปได้ (Eligible Approvers)** เพื่อทดสอบว่าระบบส่งงานไปหาถูกคนหรือไม่ (เช่น ถ้าส่งไปให้ ผจก.ภาค เขต 1 ระบบต้อง List รายชื่อ ผจก.ภาค เขต 1 ออกมาให้เห็นว่าใครบ้างที่กดปุ่มอนุมัติงานนี้ได้)
